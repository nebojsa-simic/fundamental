# Design: Math Rotary Primitive

## Context

The math module currently provides vectorized `_f32` functions implemented in
`arch/math/avx2/vector.c` (silu, swiglu, rms_norm, softmax, matrix_vector,
dot, exp, log, sin, cos). These functions are compiled with `-mavx2 -mfma`
and have no scalar fallback in `src/math/math_scalar.c`; non-AVX2 builds
simply do not link them. The demo and tests compile `vector.c` directly.

The gpt-demo RoPE code applies, for each head, a rotation:

    out[j]       = x[j]*c[j] - x[j+half]*s[j]
    out[j+half]  = x[j]*s[j] + x[j+half]*c[j]

where `half = head_dim / 2` and `c/s` are cos/sin of the positional angles.
This rotation is identical across heads and is the reusable core of RoPE.
The demo currently re-derives the theta series and cos/sin tables for every
head (64 + 8 times per layer per token) and applies the rotation in scalar.

## Goals / Non-Goals

**Goals:**
- Add `fun_math_rotary_f32()` as a reusable AVX2 primitive with scalar tail.
- Make the demo compute the theta series and cos/sin once per call.
- Remove the per-call `exp`/`log` and the serial `the *= theta_scale`
  recurrence from the hot path via a one-time precomputed table.
- Verify with golden values generated from a scalar reference.
- Preserve demo generation output (greedy argmax token sequence).

**Non-Goals:**
- Scalar fallback for `_f32` functions (consistent with all existing ones).
- Runtime CPU feature dispatch (existing `_f32` functions do not use it).
- Vectorizing the attention score/v-accumulation loops (separate follow-up).
- Changing the model-specific RoPE constants or formulas.

## Decisions

### 1. Kernel API Shape
**Decision:** `void fun_math_rotary_f32(const float *x, const float *cosv,
const float *sinv, float *out, size_t n_heads, size_t half);`

`x` is laid out as `n_heads` contiguous blocks of `2*half` floats (head h
occupies `[h*2*half, (h+1)*2*half)`). The kernel applies the rotation to
every head with a shared `cosv`/`sinv` table of length `half`.

**Rationale:** A single call covers all heads, the caller controls the
per-model constants (theta scale, ramp, mscale stay in the demo), and the
function is generic enough to be reusable. Processing the whole buffer with
pairs `(j, j+half)` is incorrect because for `j` in the second half of a head
block, `j+half` crosses into the next head - hence the explicit head loop.

**Alternatives Considered:**
- Per-head calls with `n = half` - more call sites, same throughput.
- Passing a stride - adds complexity, no benefit for contiguous blocks.

### 2. In-Place Support
**Decision:** `out` may alias `x` (in-place is safe).

**Rationale:** Within each 8-lane group, both source values (`x[j]`,
`x[j+half]`) are loaded before either store; blocks are independent. The demo
rotates `qbuf`/`kbuf` in place.

### 3. Precomputed Table
**Decision:** `Model` gains `float *rope_pre` (length `half`) computed once in
`model_load`:

    pre[j] = pow(theta_scale, j) * (ramp[j] + (1 - ramp[j]) / 32) * mscale

The theta series is a geometric series (`the_j = pos * theta_scale^j`) and
the ramp blend is a static per-j factor, so `the_arr[j] = pos * pre[j]`
replaces the recurrence, the clamps, and both per-call `exp`/`log` calls.
`mscale` is folded in so the cos/sin output is directly the scaled table.

**Rationale:** Removes the serial dependency chain and all per-head
redundancy. Mathematically equivalent; not bit-identical to the old
recurrence (FMA association differs), but within tolerance and preserves the
greedy argmax token sequence.

### 4. Numeric Verification
**Decision:** Golden values generated by extending
`tests/math/tools/generate_golden.c` with `gen_vector_rotary()`, using the
exact scalar rotation formula (plain C mul/add) as the reference; tests
compare with the existing `_math_test_check_float` tolerance pattern
(1e-4 abs / 1e-3 rel). Case shapes cover half values below, at, and above
the 8-lane boundary.

**Rationale:** Matches the existing golden-value workflow exactly; the
rotation formula contains no transcendental functions, so the scalar
reference is effectively exact and the AVX2 FMA path is compared with
tolerance.

## Risks / Trade-offs

**[Numerical association]** -> `pos * (ts*ts)` vs `(pos*ts)*ts` may differ
in the last ulp. Mitigation: tolerance-based tests, demo verification by
greedy argmax sequence equality, not bit equality.

**[Buffer size assumption]** -> The old code used `float the_arr[32]` and
would overflow for `head_dim > 64`. The refactor removes the fixed-size
arrays (buffers allocated per call like the existing `scores` buffer), which
is strictly safer.

**[AVX2-only availability]** -> `fun_math_rotary_f32` is only linkable on
AVX2 builds, like every other `_f32` function. Acceptable by precedent.

## Migration Plan

Not applicable - new additive API, demo refactor verified by output
equality.
